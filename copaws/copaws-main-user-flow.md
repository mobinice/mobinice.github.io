## 原型畫布規格

後續 HTML 原型請參考 iPhone 14 Pro Max 類似比例，但畫布固定使用：

- 寬度：428px
- 高度：939px

所有 UI 都必須在 428px × 939px 下檢查，不能超框、重疊或跑版。

HTML 原型另需支援主流實際裝置尺寸：Apple iPhone、Samsung Galaxy 手機，以及 Apple iPad 直向與橫向。配對頁的略過、收藏與預約三個操作按鈕必須始終位於底部導航上方，不可被瀏覽器工具列、底部安全區或導航遮蔽；各尺寸均不得產生水平溢出。

註冊頁在主流手機瀏覽器的可用高度下，首次進入就必須完整看到「註冊」主按鈕，不要求使用者先向下捲動。短視窗優先縮減垂直間距、卡片內距與欄位高度，不能刪減欄位；只有極短舊裝置或系統放大文字造成內容確實放不下時，才啟用垂直捲動備援。

Logo、人物頭像、寵物照片與寵物保母照片均需使用穩定的容器尺寸及 `aspect-ratio`。品牌 Logo 使用 `object-fit: contain`，使用者上傳與內容照片使用 `object-fit: cover`；裝置寬高改變時可以調整容器大小或裁切範圍，但不得把原始圖片拉長或壓扁。

- UI 05B 附近寵物保母二級列表只顯示姓名、星級評價與距離，不顯示任何預約時間。
- UI 11 收藏寵物保母頁只呈現已收藏名單，移除「已收藏幾位」摘要卡、NEW 角標與「其他可考慮人選」區塊；頁面標題下方直接提供「保母篩選」文字欄位，預設提示為「輸入寵物保母名字」。
- 收藏寵物保母清單固定依收藏時間由新到舊排序，後收藏者排列在越上方；清單採每頁 20 筆的滾動載入，第 21 筆起視為第二頁，以此類推。
- 使用者從收藏清單第二頁或後續頁面進入寵物保母詳情後返回時，系統必須保留原分頁、已載入資料與原捲動位置，不可跳回第一頁頂端。
- 待平台撥款訂單可立即完成並評價；星級必填且預設 5 星，未選星為灰色。7 天未確認時自動 5 星完成並撥款。
- 每筆交易可查看六階段進度；已完成交易可查看收據。電子發票依序顯示寵物保母服務收據、平台服務費發票、發票日期、發票號碼與四位數隨機碼。

## 核心產品主線

Copaws 的主流程應該圍繞一件事：

讓需求方打開平台後，可以依當下需求選擇「快速發需求」或「自己挑寵物保母」。時間已確定的需求方先填日期、時段、區域與照護內容，讓符合條件的寵物保母主動接案；重視特定人選的需求方則保留既有卡片、地圖與時段探索流程。服務完成與撥款後，再把評價回寫到寵物保母排序與熱度指標。

主線可以整理為：

```text
開啟平台
→ 選擇身份 / 登入
→ 手機號碼驗證
→ 進入配對首頁
→ 選擇快速發需求 / 自己挑寵物保母
→ 快速發需求：日期與時段 → 指定區域 → 寵物與照護內容 → 等待符合條件的寵物保母接案
→ 自己挑寵物保母：滑動卡片 → 收藏 / 略過 / 查看時段 → 列表 / 地圖輔助探索 → 選擇日期與時段
→ 確認寵物保母與需求內容
→ 確認預約與付款
→ 寵物保母接單
→ 到府照護與回報
→ 平台撥款
→ 需求方評價
→ 評價回寫到綜合評分與熱度排序
```

## 需求方主流程

### 1. 註冊 / 登入

Copaws 需要設計註冊登入流程，需求方與照護者共用入口，但後續導向不同身份流程。

登入方式建議以手機號碼為主：

- 輸入手機號碼
- 發送簡訊驗證碼
- 輸入驗證碼
- 驗證成功後進入配對首頁或回到原本要做的動作
- 可選擇需求方或照護者身份

測試版可以先做假驗證：

- 點擊「取得驗證碼」後自動填入測試驗證碼
- 測試驗證碼可先固定為 123456
- 顯示 60 秒倒數
- 60 秒後才能重新發送驗證碼
- 倒數中按鈕 disabled，避免連續重送
- UI 03「建立基本資料」在主流 iPhone／Galaxy 短瀏覽器視窗中，註冊按鈕需直接出現在首屏；表單保持兩欄／單欄既有資訊結構，僅調整垂直密度。
- UI 03 的生日、性別與興趣欄位一律使用既有共用選擇彈窗，不使用瀏覽器原生日期或下拉選單；整個欄位需同時支援手機觸控與電腦滑鼠開啟。
- 生日依序選擇西元年、月份與日期，最後確認後回填；性別與興趣使用單選列表，確認後回填，關閉彈窗則保留原值。

登入觸發時機：

- 第一次開啟 App 可先顯示登入入口
- 未登入也可瀏覽配對首頁
- 使用收藏、查看完整時段、預約、付款、評價前需要登入

### 2. 開啟首頁 / 配對首頁

需求方打開 Copaws 後，第一眼應該看到像交友軟體 Tinder 一樣的「照護者配對卡」，而不是先被表單擋住。

第一頁的目標是讓用戶快速感覺：

- 附近真的有人可以照顧
- 這些人看起來可信任
- 我可以很快找到有空的人

首頁需要包含：

- 需求方 / 照護者登入入口
- 所在區域，例如台北、台中
- Tinder 式照護者配對卡
- 收藏 / 略過 / 查看時段
- 附近照護者與熱門照護者
- 快速提出需求入口

首頁保留兩種互補入口：

- `快速發需求`：適合日期、時段或服務區域已確定，希望快速找到可接案人選的需求方。
- `自己挑保母`：保留既有 UI 04 的配對卡、收藏、地圖、詳細資料與時段選擇流程。
- UI 04 顯示「自己挑保母」選中；點擊「快速發需求」先進入 UI 04B 需求列表，從右上角新增按鈕才進入 UI 04A 建立需求。
- UI 04 標題改為「找寵物保母」，不再以「附近寵物保母」作為單一路徑標題。
- UI 04 與 UI 04B 的雙模式切換列縮為 `312px`，右側以 `8px` 間距配置 `48px` 共用篩選按鈕；篩選按鈕右緣固定對齊 UI 04 上方收藏按鈕右緣，兩頁切換時不得產生高度或水平位移。
- UI 09 的篩選按鈕維持右側水平位置，但垂直位置需與「我的預約」標題區同列，不可獨占下一行；預約卡片從標題區下方直接開始排列。
- 移除 UI 04 主畫面的地區／今日可約／寵物類型標籤、UI 04B 的需求狀態標籤列，以及 UI 09 的文字狀態列；釋出的垂直空間由配對卡、需求卡與預約卡向上補齊。

### 2A. 快速發需求 / 需求優先配對

快速發需求採單頁、可垂直捲動的最小表單，不要求需求方先逐一查看寵物保母日曆。

表單包含：

- 服務日期月曆
- 點擊年月標題開啟 UI 04A-1 年月選擇彈窗；年份與月份在同一畫面完成選取，確認後回填 UI 04A 月曆
- 不提供過去年份；選擇當年度時，過去月份置灰不可選，當月中早於今日的日期同樣不可選
- 開始時間與結束時間各自使用共用時間彈窗，不顯示上午、下午、晚上或自訂快捷按鈕
- 兩個時間預設皆為 `00:00`；滑鼠點擊與手機觸控都必須能開啟同一套時間彈窗
- 結束時間不得小於開始時間；前端在選擇與送出時阻止無效區間，NestJS 在建立或修改需求時再次驗證
- 指定縣市與行政區；兩個欄位分別使用底部選擇彈窗，滑鼠與觸控點擊整個欄位皆可開啟，不使用瀏覽器原生下拉選單
- 寵物資訊
- UI 04A 的「寵物資訊」沿用 UI 08C／09D-1 共用選擇寵物彈窗，不使用瀏覽器原生下拉選單；選擇並確認後回填欄位、需求摘要與送出資料。
- 若尚未建立寵物資料，UI 04A 顯示「建立寵物資料」入口；完成新增後返回 UI 04A，刷新選項並保留原本已填需求內容。
- 餵食、清砂、陪玩、其他等協助事項
- 需求補充文字
- 輸入本次照護費；平台服務費依當下可取得的適用費率估算，無優惠時預設為照護費的 15%，額外向飼主收取，輸入後即時計算平台服務費與付款總額
- 送出前的日期、時段、區域、寵物、任務與費用摘要
- 建立或修改需求時，NestJS 依台北時區再次驗證服務開始時間不得早於當下，避免繞過前端限制送出過去日期

送出後：

- 建立「等待接案」的需求資料，並進入 UI 04B「需求列表」。
- UI 04B 屬於配對流程，不取代 UI 09「我的預約」；底部「預約」仍只開啟原本的預約與訂單狀態頁。
- UI 04 與 UI 04B 是同一層的配對首頁頁籤：UI 04 顯示「自己挑保母」選中，UI 04B 顯示「快速發需求」選中，兩頁可直接互相切換。
- UI 04B 不顯示返回按鈕；右上角 `+` 進入 UI 04A，UI 04A 左上角返回 UI 04B。
- UI 04A 是建立需求的子頁，不顯示「快速發需求／自己挑保母」切換列；該切換列只保留在 UI 04 與 UI 04B 兩個同層入口頁。
- 需求列表依建立時間由新到舊排列，每筆以卡片顯示服務地點、服務日期與時間、服務內容及照護費。
- 每張需求卡提供編輯與刪除圖示；新增需求按鈕可返回 UI 04A 建立下一筆需求。
- 點擊編輯進入 UI 04C「修改需求」，畫面依 UI 09D 的欄位、間距與金額統計規格呈現，並預填原需求內容；服務日期、寵物資訊、縣市與行政區都必須使用各自的底部選擇彈窗，確認變更後返回需求列表並重新開放媒合。
- 點擊刪除進入 UI 04B-1 刪除確認狀態，沿用選擇寵物的遮罩與底部白色面板樣式，顯示被刪除需求的完整摘要後才允許確認刪除。
- 刪除彈窗的取消、關閉與確認操作皆返回 UI 04B；實際原型串接時，只有確認刪除會移除需求資料。
- 當需求收到申請時，UI 04B 顯示「已有 3 位申請」示例；點擊需求卡進入 UI 04B-2，逐一查看申請保母並選擇接受或婉拒。
- UI 04B 使用黃色「等待接案」、藍色「已有申請」與綠色「已配對成功」三種狀態色；UI 04B-2 頁首直接沿用列表中的完整需求卡，不重複製作精簡摘要。
- 申請保母資訊遵循統一保母卡順序：姓名與認證、黃色星級與評價數、瀏覽／距離／服務類型及簡介。
- 點擊申請保母卡的資訊區可進入 UI 06 保母詳情；返回時必須回到 UI 04B-2 申請頁並保留原捲動位置，不得跳回配對首頁或需求列表。
- 接受申請後進入已配對成功狀態，同步建立或綁定穩定的 `booking_id`，需求卡移除編輯與刪除操作；點擊卡片可進入 UI 04D 查看已配對保母與完整服務內容。
- 已配對成功卡另顯示「跳轉預約看進度 →」；點擊後直接進入 UI 09「我的預約」，切回全部狀態、捲動定位對應預約卡，並以綠色外框持續提示，離開預約頁後才清除。正式資料需以穩定的 `booking_id`／`order_id` 建立需求與預約對應，不可用姓名或畫面排序推測。
- UI 09 每一張預約卡都必須顯示「查看需求」；點擊後才進入 UI 09C「需求詳情」。進行中、即將服務、需求確認中、待服務與待撥款原有的回報、聯絡、提醒、修改與評價操作仍保留。
- 保母接受需求後，預約先進入「待雙方見面」階段，不直接進入即將服務。UI 09 顯示對應卡片與「確認已見面」操作；飼主必須勾選「我確認已與寵物保母完成實體見面」後才能送出確認。
- 飼主與寵物保母各自保存見面確認時間；只有雙方都完成確認，後端才可將預約從 `meeting_pending` 推進至 `upcoming`。單方確認、只有前端勾選或未保存確認紀錄時，都不得開始後續服務。
- 婉拒申請時開啟 UI 04B-3，使用置中彈窗選擇必填理由，並可輸入選填補充說明；彈窗不提供星級評分。
- UI 04D 在距離服務開始超過 3 天時顯示可操作的取消配對按鈕；UI 04D-1 表示進入服務開始前 3 天區間，按鈕置灰且不可操作。
- 可取消時先進入 UI 04D-2「取消配對確認」，顯示需求、保母與重新媒合提示；暫不取消返回 UI 04D，確認取消才送出後端操作。
- 取消成功後需求進入 24 小時重新媒合保留期，保母端在 `reopen_at` 前不可看到該需求；滿 24 小時後才重新曝光給符合條件的寵物保母。
- 實際取消流程必須由 NestJS 依服務開始時間檢查資格、記錄取消狀態與 `reopen_at`，並控制保母端曝光；前端不得自行決定取消結果或重新開放時間。
- UI 04A 的「送出需求，開始配對」完成送出後進入 UI 04B；UI 04A 與需求子流程只維持底部「配對」導航選中，不重複顯示頂部媒合方式切換列。
- 只推送給已通過寵物保母審核，且服務日期、時段、區域、寵物類型與可服務狀態符合的寵物保母。
- 寵物保母端快速接案卡顯示距離、日期與時段、服務區域、寵物、協助事項、需求補充與本次照護費。
- 寵物保母可以略過或接受需求；點擊接受時先開啟置中確認彈窗，必須勾選「我已閱讀並同意安排雙方實體見面」才能確認接案。
- 接受需求彈窗保留「查看保母服務說明」入口；服務說明內容後續補齊，但入口固定使用既有置中彈窗樣式，不開新頁或另做一套元件。
- 寵物保母接受後先進入「待雙方見面」，並在案件頁確認已完成見面；雙方確認完成後才銜接既有的即將服務、服務進行與付款流程。
- 寵物保母在服務尚未開始前可以取消已接受的需求；接單前不接受案件仍使用 `rejected_by_sitter`，接單後由保母取消則使用 `cancelled` 並記錄取消角色、原因與時間，不得混為同一狀態。
- 保母取消成功後，依目前累計取消次數套用新配對冷卻：第 1 次為 1 天、第 2 次為 3 天、第 3 次及之後皆為 7 天。冷卻期間不得接受快速需求、不得被飼主直接預約，也不得與任何新飼主建立配對；既有已成立案件不因冷卻自動取消，仍依各自訂單狀態執行。
- 冷卻期與保母已儲存的可服務時段有任何時間重疊時，重疊區間在飼主端日曆自動反灰且不可操作；系統只套用禁用結果，不刪除保母原本的可服務設定。冷卻結束後，未被其他訂單占用且仍有效的時段自動恢復可預約。
- 取消次數採連續紀錄：從最近一次保母取消時間起，連續滿 30 天沒有再次取消，次數才重設為 0，下一次取消重新視為第 1 次並套用 1 天冷卻；30 天內再次取消則遞增次數，且每次取消都重新起算這個 30 天無取消重設期間。
- 每次保母取消都由 NestJS 在同一交易內鎖定保母資料、判斷是否已滿 30 天可重設、遞增取消次數，並依第 1／2／3 次以上計算 `matching_blocked_until = cancelled_at + 1 / 3 / 7 days`。有效冷卻不得由前端自行解除、縮短或繞過，計算結果需寫入訂單快照供客服與稽核追查。
- 快速發需求不取代既有自行挑選流程，需求方可隨時切換回 UI 04。

### 3. 配對卡互動

配對卡是需求方第一個主要互動。

建議互動：

- 右滑 / 點愛心：收藏或加入候選
- 左滑 / 點略過：暫時不看
- 左滑時在畫面左側顯示紅色圓形 `×`，右滑時在畫面右側顯示綠色圓圈；提示強度跟隨拖曳幅度。
- 滑動成功後，卡片離場、O／X 提示清除與下一張卡片解鎖必須同步在約 200ms 內完成；提示消失後可立即開始下一次滑動。
- 配對卡必須支援快速連續左右滑動，不可因前一張動畫尚未清理而卡住、跳過或顯示空白。
- 下一位寵物保母卡需預先顯示在後方，隨拖曳幅度由縮小、下沉狀態逐步推近；前卡離場後無縫成為完整主卡。
- 觸控可從卡片中央、照片、文字或邊緣任意位置開始水平滑動；只有水平意圖成立後才捕捉指標，避免右側起手時的觸控取消座標被誤判為瞬間左滑。
- 觸控滑動同時採距離與速度判定：一般拖曳達水平距離門檻即換卡；方向一致的快速短滑可用速度門檻成立；慢速短滑回彈。`pointercancel` 不得使用不可靠的取消座標，但先前移動事件已確認達門檻的水平手勢仍可完成換卡；不可靠的 touch capture 遺失則取消。
- 右滑收藏不得在卡片離場動畫開始前同步重建收藏清單；收藏頁於進入時再依最新資料渲染，確保左右滑的跟手性與動畫流暢度一致。
- PC 滑鼠拖曳必須處理移出卡片／瀏覽器後放開、`pointercancel`、失去 pointer capture、視窗失焦與延遲動畫幀；放開位置不可影響判定，達到水平門檻即完成換卡，未達門檻則回彈。
- 卡片保留垂直捲動手勢；從卡片中央上下滑動時不可誤觸左右換卡。
- 一旦同一 pointer sequence 已被判定為水平拖曳、垂直捲動或取消手勢，該序列後續合成的 click 必須被消耗，不得再開啟詳情；只有未超過意圖門檻的正常輕點可以進入詳情。
- 配對卡採前後雙卡預載，快速或連續滑動時不可出現空白卡片。
- 點卡片：進入照護者詳細頁
- 點日曆：直接查看可用時段
- 點地圖：切換到附近地圖

配對卡需要呈現：

- 大頭像或生活照
- 名稱
- 距離
- 認證圖示（平台認證優先，無平台認證時顯示實名認證）
- 星級與評價數
- 熱度指標
- 最近可預約時間
- 可服務寵物類型
- 一句個人介紹

### 4. 區域列表 / 地圖探索

需求方可以用兩種方式找照護者：

- 列表模式：適合比較評價、價格、距離、可預約時間
- 地圖模式：適合快速看誰離自己家最近

地圖模式的保母浮動摘要與附近保母列表只顯示：

- 距離
- 評價星級
- 綜合評分

地圖模式不顯示今日、明日、近期或最近可預約時間，避免資訊過密。地圖頁每次進入時回到頁首，標題與副標題固定在手機安全區下方並完整顯示。

地圖浮動寵物保母摘要卡需與下方附近保母列表使用相同資訊結構：頭像、姓名與認證／星級評價、距離。姓名從資訊欄左緣開始，不保留多餘前置空白；認證圖示固定接在姓名實際渲染右緣後 8px，並遵守「平台認證優先，沒有平台認證才顯示實名認證」規則。

### 5. 照護者卡片

照護者卡片是需求方快速判斷是否點進去的關鍵。

卡片建議包含：

- 頭像
- 名稱
- 認證標章（平台認證優先，無平台認證時顯示實名認證）
- 星級與評價數
- 距離
- 熱度指標
- 可服務寵物類型
- 最近可預約時間
- 今日 / 明日是否有空
- 起始價格
- 查看時段 / 查看詳細

### 6. 照護者詳細頁

需求方點進照護者資料後，要能直接判斷三件事：

- 這個人是否可信任
- 這個人是否適合我的寵物
- 這個人什麼時候有空

詳細頁需要包含：

- 個人介紹
- 認證狀態（平台認證優先，無平台認證時顯示實名認證）
- 養寵與照護經驗
- 可服務區域
- 可服務寵物類型
- 星級評分
- 需求方評價
- 服務次數
- 熱度指標
- 可用時段日曆
- 立即預約

### 7. 可用時段日曆

日曆是從「看資料」轉成「預約」的核心。

日曆需要支援：

- 日期切換
- 週 / 月視圖
- 點擊年月標題開啟月份彈窗；只列出該寵物保母已設定可服務時段的月份
- 若目前月份之後沒有任何可服務月份，隱藏右側箭頭，避免讓需求方誤以為仍可切換
- 上午 / 下午 / 晚上時段
- 已被預約時段不可選
- 可選時段高亮
- 選定時段後進入需求填寫
- 若時段不可用，推薦同區域其他照護者

### 8. 填寫照護需求

選好照護者與時段後，需求方再填寫照護需求。

需求表單應該包含：

- 寵物選擇
- 服務地址
- 照護時間
- 服務類型
- 餵食 / 散步 / 陪伴 / 清潔等任務
- 特殊注意事項
- 補充照片

### 9. 預約與付款

需求方確認預約資訊並付款。

需要顯示：

- 照護者
- 日期與時段
- 地址
- 寵物
- 服務內容
- 價格明細
- 平台保障
- 取消政策
- 付款方式

### 10. 服務進行中

服務進行中，需求方需要看到安心感。

需要包含：

- 照護者已接單
- 出發狀態
- 到達打卡
- 照護任務進度
- 照片 / 文字回報
- 緊急聯絡
- 完成服務

### 11. 撥款後評價

平台完成撥款後，需要觸發評價機制。

評價需要包含：

- 星級
- 文字評價
- 是否準時
- 是否照顧細心
- 溝通是否清楚
- 是否願意再次預約

評價結果會回寫到：

- 照護者綜合評分
- 評價數
- 熱度指標
- 區域熱門排序
- 後續媒合權重

## 寵物保母主流程

### Figma MVP 畫面對照

寵物保母端以 B 系列畫面集中管理，資訊架構、欄位、卡片、篩選及彈窗直接沿用已核准的飼主端規格，不建立另一套元件。

- `B01 保母快速接案`：顯示符合服務區域、已儲存可服務時段及寵物類型的需求卡；標題列只保留共用篩選 icon，不再外露「接案中」或地區、日期、寵物、距離條件籤。
- `B01-1 保母地圖探索`：沿用飼主端 UI 05 的地圖、標記、選中摘要與附近列表版型，將內容改為已發布有效需求的飼主；地圖與 B01 使用同一套可接需求資格規則。
- `B01-2 保母地圖飼主列表分頁`：沿用飼主端 UI 05B 的完整列表與分頁版型，顯示全部符合條件且具有有效需求的飼主。
- `B02 可接需求詳情`：顯示飼主、寵物、日期時段、地址、協助事項、注意事項及本次照護費，可接受或婉拒需求。
- `B02-1 婉拒需求確認`：沿用既有置中彈窗，提供快捷理由、補充說明、返回及確認婉拒。
- `B02-2 接受需求確認`：顯示必選的實體見面同意框、雙方確認規則、服務說明入口、返回與確認接受；未勾選時確認按鈕置灰。
- `B02-3 接受需求確認・已勾選`：展示勾選後可送出的按鈕狀態。
- `B02-4 保母服務說明`：沿用置中彈窗並保留後續正式說明內容位置。
- `B03 我的案件`：集中顯示需求確認中、待雙方見面、即將服務、進行中、待撥款等案件狀態；服務開始前的已接受案件可依規則發起保母取消。
- `B03-1 我的案件篩選`：使用共用篩選 icon 與置中彈窗，篩選案件狀態、服務日期及服務地區。
- `B03-2 確認雙方已見面`：寵物保母勾選確認實體見面；未勾選時不可送出。飼主端 `09E` 與保母端 `B03-2` 必須共用同一彈窗格局：64px 摘要頭像、24px 勾選框、單行 20px 確認文字與勾選框垂直置中，分隔線、補充說明及底部雙按鈕使用相同間距，不得因角色文案不同留下額外空白。兩端摘要皆依固定卡片順序顯示姓名與認證、黃色星級與評價總數、寵物資訊；見面規則文案統一為「接受後，需由你與飼主分別確認完成見面，案件才會進入即將服務。」並在下方提供既有「查看保母服務說明 ›」入口。B03-2 的彈窗高度、說明區與按鈕位置需同步 09E，不保留舊版額外留白。
- `B04 進行中服務詳情`：顯示服務進度、飼主與寵物摘要、時間、地址及聯絡／回報／完成服務操作，時間軸保留「雙方已確認見面」事件。
- `B05 新增服務回報`：選擇回報項目、上傳照片、填寫文字及回報時間。
- `B06 聯絡飼主`：沿用既有留言板、快捷回覆、已讀／送達及敏感資料提醒規格。
- `B07 可服務時段`：日曆尺寸、星期列、日期圓形、已設定外框、目前選取實心及不可用反灰狀態必須直接沿用飼主端 `UI 07 選擇時段`，不可維護另一套保母日曆樣式。寵物保母先選日期，再分別選擇開始時間與結束時間並新增一個或多個可服務時段；只有已儲存的日期與時段會出現在飼主預約與快速需求媒合結果中，未儲存即視為不可預約。MVP 不提供手動新增不可服務時段、例外日或請假設定入口；保母取消案件依次數產生的 1／3／7 天冷卻屬系統禁用區間，與已儲存時段重疊時必須自動反灰且不可預約。
- `B08 收入與撥款`：顯示可撥款餘額、待撥款與交易紀錄，標題列使用共用篩選 icon。
- `B08-1 收入交易篩選`：沿用共用篩選彈窗，篩選交易狀態、交易類型及時間範圍。
- `B08-2 收入交易明細`：顯示案件時間軸、寵物保母服務費、訂單實際平台服務費率及實際撥款。
- `B09 寵物保母個人中心`：管理平台／實名／手機認證、服務設定、時段、收入與撥款、評價及成長資訊。
- `B10 編輯寵物保母檔案`：管理固定比例照片、服務介紹、寵物類型、服務項目、地區、照護費及經驗。
- `B09 寵物保母個人中心` 的個人資料卡必須直接沿用需求方 UI 10 的卡片結構：上傳大頭照按鈕尺寸一致，平台、實名與手機認證三個 32px 圖示固定水平排列在卡片右上角，不可放在姓名或角色文字下方。
- `B11 評價與成長`：顯示整體評分、服務品質指標、近期變化及飼主評價。

保母端所有飼主摘要卡與彈窗內精簡摘要，包含 B01、B02、B02-1、B02-2、B02-3、B02-4、B03-2、B04、B05 與 B06，必須共用同一套卡片標準：

- 頭像以 UI 04 默認人物頭像為唯一基準，背景綠、人物米白、黃色識別點的色值、比例與縮小版本均不得另行重畫。
- 第一行固定為「飼主姓名＋認證圖示」，認證圖示接在姓名實際渲染右緣後 8px；有平台認證時顯示藍色平台認證，沒有平台認證時才顯示實名認證。
- 第二行固定為黃色星級、數字評分與總評價數；不得以「手機已驗證」文字或膠囊取代認證與評價資訊。
- 第三行固定為寵物名稱、種類、年齡與性別摘要；資訊列底部不得超過頭像底部，彈窗中的精簡卡同樣適用。
- 同一個飼主摘要只能展示一種最高優先級認證，不得同時堆疊平台、實名及手機認證標籤。

所有 B 系列列表、詳情及交易頁同樣套用 G01 全域空資料與重新載入狀態。共用篩選 icon、遮罩、面板、關閉、清除及套用操作必須與飼主端一致；來源頁只替換篩選內容。

保母端需求地圖與快速接案遵循以下規則：

- 飼主只有在至少一筆需求已成功發布且仍有效時，才會出現在保母端地圖；需求被刪除、取消、配對、逾期，或仍在 `reopen_at` 重新媒合保留期時，必須立即從地圖及 B01 可接序列移除。
- 地圖標記代表一筆有效需求，不代表飼主永久位置。同一飼主有多筆有效需求時可以有多個標記，但每個標記都必須綁定穩定的 `demand_id`。
- 地圖只使用需求中的縣市、行政區及官方行政區代碼，不在接案前顯示或推算精確地址。散點位置由「行政區代碼＋demand_id」產生穩定結果，重新整理、重新登入及跨裝置不得任意跳動。
- 同一行政區有多筆需求時，在行政區範圍內進行穩定錯位排列；標記之間至少保留一個完整 pin 寬度加 8px，不能互相重疊或移出行政區。空間不足時改用數量聚合點，放大後再展開。
- B01 的地區、服務日期及寵物類型等條件全部收進既有共用篩選彈窗；移除頁首「接案中」狀態，不另外建立接案開關。保母是否可接案仍由審核、停權、有效的 1／3／7 天取消冷卻、服務區域、已儲存時段及寵物類型共同判斷。
- B01 整張飼主需求卡皆可左右滑，照片、文字與卡片邊緣使用同一手勢區。左滑等同略過，只移出本次瀏覽序列；右滑只開啟既有接受需求確認彈窗，完成實體見面同意勾選及後端確認後才算接案成功。
- B01 必須與需求方 UI 04 共用前後雙卡堆疊。下一筆需求預先渲染在後方，但未拖曳時保持 `opacity(0)` 而不可見；開始左右拖曳後，隨幅度由 `translateY(18px) + scale(.94) + opacity(0)` 線性推進至完整尺寸與不透明。前卡離場後，後卡無空白幀接成主卡並預載再下一筆。
- B01 與需求方 UI 04 必須共用同一手勢判定：8px 後辨識水平／垂直意圖，一般水平拖曳達 92px 完成，觸控方向一致的快速短滑至少 42px 且符合相同速度門檻才可完成；其餘拖曳回彈。垂直手勢保留頁面捲動，滑鼠移出卡片後放開仍依已追蹤位移判定。
- B01 一旦開始水平拖曳、垂直拖動或收到取消／失去 capture，該次手勢後續 click 必須被消耗，不得因卡片的詳情連結而自動開啟 B02；正常輕點仍進入需求詳情。離場或回彈動畫未清理前不得重複換卡或導覽。
- 略過與接受按鈕仍保留給滑鼠、鍵盤及無障礙操作。接受時若需求已被其他保母取得，顯示需求已失效並載入下一筆，不得建立重複案件。
- 點擊地圖標記顯示需求摘要，摘要顯示飼主、認證、評價、服務行政區、日期時段、寵物、協助事項與照護費；從摘要進入 B02 後返回，須保留地圖中心、縮放、篩選與選中項目。
- B01-1 上方「需求地區」整個欄位皆可點擊，先開啟既有 `G02-1 共用篩選・選擇城市`，選定城市後進入 `G02-2 共用篩選・選擇行政區`；確認行政區後返回 B01-1 並更新地圖、標記與列表，不新增另一套地區彈窗。
- B01-1 選中飼主摘要同樣套用保母端飼主卡標準；飼主姓名與認證 icon 的實際渲染間距固定為 8px，不得覆蓋姓名、評價或右側行政區。
- B01-1 的附近列表固定先顯示排序後前 20 位飼主；總數超過 20 位時才顯示「查看更多」，點擊後進入 B01-2，不在原頁繼續向下堆疊資料。
- B01-2 每頁固定顯示 8 位飼主，需顯示目前頁碼、總頁數及本頁資料範圍；第一頁停用上一頁，最後一頁停用下一頁。
- B01-2 的飼主列顯示排名、固定人物頭像、姓名與最高優先認證、黃色星級、數字評分、總評價數及需求行政區。點擊後進入 B02，返回時保留原分頁及捲動位置。

寵物保母端底部導航固定為四項：「接案、地圖、行程、個人」，每欄等寬 107px。接案沿用 B01 愛心圖示，地圖完整沿用飼主端地圖圖示的未選／選中狀態，行程完整沿用飼主端日曆圖示，個人使用 `$` 圖示但文字仍顯示「個人」。收入不設獨立底部入口，從 B09 個人中心的「收入與撥款」進入 B08；所有 B 系列含底部導航的畫面必須共用相同四等分寬度、圖示位置、標籤、安全區與選中狀態。

### 3. 實名認證

寵物保母必須完成實名制，審核通過後才能接案。個人設定中的「成為寵物保母」點擊「開始認證」後，進入 UI 10I「實名認證審核」。

流程包含：

- 手機號碼驗證
- 手機 / Email 驗證
- 實名資料填寫：本名、生日（西元年、月、日）、身分證字號、身分證換／補發日期（月、日）
- 點擊生日的西元年、月份或日期欄位時，分別開啟對應的底部選擇彈窗；遮罩、白色圓角面板、選取狀態、關閉鍵與確認按鈕沿用「選擇寵物」彈窗樣式
- 西元年彈窗使用可上下捲動的年份列表；月份彈窗顯示 1–12 月；日期彈窗依所選年月顯示可用日期
- 身分證換／補發月份與日期同樣使用底部選擇彈窗；月份提供 1–12 月，日期提供 1–31 日
- 生日與換／補發日期的五個選擇欄位都必須同時支援手機觸控與電腦滑鼠點擊開啟彈窗
- 點擊「確認選擇」後回到實名認證審核頁並寫入欄位；關閉彈窗則保留原值
- 身分證正面與反面照片上傳
- 良民證照片上傳；欄位下方固定提示「請上傳 2023 年以後申請的良民證照片」
- 送出前必須勾選同意「保母服務說明」
- 點擊「保母服務說明」開啟彈窗；彈窗內容後續補充
- 送出資料並通過欄位驗證後，返回 UI 10J「個人中心・實名認證審核中」
- 個人中心原「成為寵物保母／開始認證」卡片改為「實名認證審核中／審核中」，顯示平台正在審核及完成後通知的說明
- 審核中狀態停用認證入口，不允許重複送件；待平台審核結果更新後才切換為通過或補件狀態
- 平台退回申請時切換為 UI 10K「個人中心・實名認證未通過」；卡片以退回色區分，標題顯示「實名認證未通過」，並直接展示平台回傳的退回原因。
- UI 10K 提供可操作的「再次審核」按鈕，點擊後返回既有 UI 10I 實名認證審核表單，不另建另一套補件表單；重新送出成功後狀態再次切換為審核中並停用重複送件。
- 正式資料狀態至少包含 `not_started`、`pending`、`rejected` 與 `approved`；退回原因由平台審核結果提供，前端不可自行虛構正式原因。
- 平台審核
- 認證通過標章
- 未通過原因與重新提交

送出後資料進入平台審核流程，原型在同一瀏覽器工作階段內保留審核中狀態，並以 `identity-review=rejected` 展示退回狀態供驗收；再次送件後恢復審核中。所有身分及證件資料僅供平台進行身分與寵物保母資格審核，上傳之所有文件平台不會另作他途，並依資料安全規範妥善保管。

### 4. 可服務時段管理

寵物保母可以設定自己能接案的時間。

- 操作順序固定為選擇日期、選擇開始時間、選擇結束時間、儲存時段；結束時間必須晚於開始時間。
- 同一天可以建立多個不重疊時段；新增時需阻擋重複或交疊區間。
- 每一個已儲存時段最多只能配對一筆需求。尚未配對時只顯示「可配對」；配對成功後整個時段只顯示「已配對」，並自動反灰禁用。兩種狀態都不顯示筆數，亦不顯示「已鎖定」文字；已配對時段不可再被其他飼主預約。
- 訂單取消、冷卻或其他系統限制不得直接刪除原始可服務設定；是否重新開放依取消與冷卻規則判斷。

包含：

- 可服務日曆
- 平日 / 假日可服務時段
- 休假或不接案時段
- 已被預約時段
- 臨時關閉接案

寵物保母接到需求後，可查看案件並接單。

流程包含：

- 行程提醒
- 出發打卡
- 到達打卡
- 任務回報
- 照片回報

服務完成後，平台撥款給寵物保母；撥款後觸發需求方評價。

寵物保母端需要看到：

- 訂單收入

- 可提領金額
- 撥款狀態
- 評價結果
- 綜合分數變化

### 6A. 後台平台服務費率設定

- 平台服務費維持由飼主在照護費外額外支付，預設費率為照護費的 15%；寵物保母服務費與應收款不得因平台費率調整而減少。
- 後台可針對指定寵物保母帳號設定個別平台服務費率。個別設定可選擇永久有效，或指定生效日與截止日；永久代表持續有效至管理者主動終止。
- 後台可設定全站平台服務費減免，例如在指定期間將預設 15% 降為 10%。全站減免不得用來提高費率，必須設定生效日與截止日。
- 後台輸入的數值為最終費率，不是折扣比例；例如 `15% → 10%` 應儲存為 10%，不可解讀為打九折或減少 10%。
- 指定保母個別費率會取代預設 15% 作為該訂單的基礎費率；若同時存在全站減免，則以全站費率作為上限。公式為 `min(個別費率或預設 15%、有效全站減免費率)`。例如個別 8% 且全站 10% 時使用 8%；個別 12% 且全站 10% 時使用 10%。
- 同一寵物保母的個別規則不得有有效期間重疊；全站減免規則之間也不得重疊。後台必須在建立或啟用時拒絕衝突，不採最後更新者覆蓋。
- 有期限規則依 `Asia/Taipei` 日曆日判定，生效日與截止日均包含當日；資料庫使用 UTC `timestamptz` 半開區間保存，截止日轉為次日 00:00 的排他上限。
- 費率在寵物保母已確定、NestJS 建立可付款訂單時鎖定。快速需求尚未配對時只能顯示全站／預設費率估算；配對完成後必須重新計價並讓飼主確認最終金額。
- 付款單建立後，後台新增、修改、到期或終止費率規則皆不得追溯改寫該訂單；付款、退款、平台服務費發票、帳務流水與客服查詢都必須沿用訂單費率快照。
- 付款單逾期、取消或失效後重新建立時，依重新建立當下的有效規則重新計價。付款前更換寵物保母時也必須重新計價。
- 費率規則狀態包含未生效、生效中、已到期、已取消及已終止。生效中的規則不得原地覆寫歷史內容，調整時需終止舊規則並建立新版本。
- 只有具「平台費率管理」權限的後台角色可建立、排程、終止或取消規則；每次操作必須記錄操作者、前後值、設定原因、適用對象、有效期間與版本。
- 費率解析、金額計算與快照建立只能由 NestJS 執行；飼主端、保母端及 Supabase Data API 不得直接寫入費率或訂單金額。
- 報價、付款確認、交易明細、收據與平台服務費發票必須顯示訂單實際套用費率，不可將 15% 寫死在畫面或帳務紀錄中。
- TWD 平台服務費的小數取整方式仍須在正式金流實作前統一定案，並由 NestJS、發票、退款與帳務流程共用同一規則。

驗收條件：

- 無個別規則及全站減免時，訂單使用預設 15%。
- 指定保母永久或期間費率只影響該保母的新付款單；其他保母維持原適用費率。
- 全站 10% 減免生效時，未設個別費率的訂單使用 10%；個別 8% 使用 8%，個別 12% 使用 10%。
- 生效日 00:00 起套用，截止日整日仍有效，隔日 00:00 起不再套用；同範圍重疊規則必須建立失敗。
- 已建立付款單的費率與金額不因規則異動而改變；失效後重建付款單則依重建當下規則重新計價。
- 無「平台費率管理」權限者不得查改完整規則；所有成功與失敗的後台變更嘗試均須留下可追蹤稽核紀錄。

## 全域資料狀態

所有會向後端取得資料的列表、詳情與交易頁，統一使用 UI G01 全域資料狀態，不在各頁重新設計不同版本。

### 空資料狀態

- API 請求成功但結果為 0 筆時顯示，不可用載入失敗文案取代。
- 固定包含空資料圖示、短標題與輔助文案。
- 主要行動依頁面情境替換，例如「開始新增」、「發出第一筆需求」；沒有合理下一步時可省略按鈕。
- 空資料狀態需保留原頁面的標題、篩選與底部導航，僅取代資料內容區。

### 載入失敗與重新載入

- 逾時、斷線或 API 回傳錯誤時顯示載入失敗狀態。
- 必須提供「重新載入」主要按鈕，並可依頁面提供「返回上一頁」次要動作。
- 重新載入需重送最後一次失敗的資料請求，保留原篩選條件、分頁、已選項目及捲動位置。
- 重試進行中按鈕顯示載入動畫並停用連點；成功後收起錯誤狀態，失敗則保留狀態並允許再次重試。
- 空資料與載入失敗是不同資料結果，不可互相誤判。
